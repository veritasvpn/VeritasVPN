Transparency

Last updated: October 25, 2026. Veritas Ark, Asunción, Paraguay. contact@veritasvpn.cloud. This page explains the controls behind the Privacy Policy. It is not a substitute for that policy, and it is not an audit.

What this page is

One operator, Veritas Ark, runs VeritasVPN. The VPN servers and the account database are in Paraguay. No independent audit report is published. The source is public under the Business Source License. A warrant canary states whether we have received a secret order we cannot describe.

Read this as a description of the code in the public repository. It is not a claim that a person with access to the machine cannot look at live state. It is not a claim that we keep zero logs, and it is not a claim that the service is RAM-only. The account database, metrics, the DNS filter list, and backups are on disk. The connecting IP is handled as described below.

What we keep

Account

  • An email address, if you register with one. An Account ID account has no email. Email is optional.
  • A bcrypt hash of the password. We do not store the password itself.
  • The Account ID, plan, subscription status, account creation time, and email verification time.
  • SHA-256 hashes of refresh tokens, email-verification tokens, and password-reset tokens. We do not store those tokens in the clear.

Access tokens last 1 hour by default. Refresh-token hashes last 7 days by default. Verification links expire in 1 hour. Password-reset links expire in 20 minutes. Email accounts that are never verified are deleted after 72 hours. That cleanup runs every 6 hours.

Device and tunnel

While a peer is pending or active, and for 30 days after it is removed, we store:

  • The WireGuard public key and a preshared key used to operate the tunnel.
  • The assigned tunnel IP, the server, the status, and the create time.
  • The last handshake time. That is a timestamp, not an address.
  • A random per-install device ID. The app creates it on the device so one account can have one peer per install, up to the plan's device limit. It is not an IMEI, Android ID, advertising ID, or MAC address. The peer-created log stores a short hash of it, not the raw value.
  • Device name, platform, model, OS version, and client version. Android sends the manufacturer and model. The Linux app may send the computer hostname as the device model. These are display data for the account, and the device ID is also how the device limit is enforced.
  • The Veritas Shield toggles for that peer.

A free account cannot create a tunnel, so Shield does not filter a free account.

Payments

  • Google Play Billing, for the Play app. Google processes the payment. We store purchase and subscription status, and the Play purchase token on the subscription row. We keep that token so we can check the purchase with Google, and so the same token is not linked to a second account. We do not send it back to the app. The payment row stores the same token as the provider transaction id, so a repeat notice updates that row instead of creating another one. We do not receive card numbers. New purchases are matched with a one-way HMAC-SHA256 of the Account ID, using a fixed public label rather than a secret key. That value is not the Account ID and cannot be used to sign in. Purchases started before this change may still be matched using the Account ID that was sent with them. Deleting the account does not cancel the Google Play subscription.
  • Bitcoin, for the website, the Linux app, and the Android app installed from this website rather than Google Play. Checkout is self-hosted BTCPay. There is no card checkout on this path. We store the amount, currency, plan, status, timestamps, and a provider transaction id against the account. That id is the BTCPay invoice id. We keep it so a later payment notice is matched to that checkout and is not applied twice. The BTCPay invoice is tagged with the account ID. A Bitcoin checkout that is still pending after 4 days is marked failed and then kept for the life of the account. Deleting the account removes our payment rows. It does not delete the invoice on the BTCPay server.

Bandwidth

The VPN node adds up bytes sent and received across peers on that server. Prometheus records those totals, and the peer count, with no per-user label. Heartbeats report the same server-wide totals, the peer count, and each peer's last handshake time. They do not report a per-user traffic history, and they do not report the connecting IP.

What we do not keep

  • Browsing history.
  • A log of the DNS names you look up. A blocked name can be held for the short windows in the Shield section. Allowed lookups are not stored.
  • The contents of your VPN traffic.
  • Your real connection IP in the account database, the connect log, or a backup. No backup contains a real user IP.

What happens to the connecting IP

When an app asks for a tunnel, that API request comes through Cloudflare. Origin nginx fills X-Real-IP from Cloudflare's connecting-IP header when that header is present, and otherwise from the immediate connection address. The account service and the WireGuard manager read X-Real-IP. They do not read CF-Connecting-IP or X-Forwarded-For themselves, because a client can spoof those headers if it can reach the app directly. They trust the address the origin proxy puts in X-Real-IP.

That address is used in memory to choose whether this response should name the on-LAN server endpoint or the public one. It is not a column on the peer. The peer-created log line, and the event published for that peer, store a short hash of the peer id, the account id, the device id, the assigned tunnel IP, and the server endpoint that was chosen. They do not store those values in the clear, and they do not store your real public IP. The hash is the first 8 bytes of SHA-256, with no secret salt. A tunnel address comes from a small pool, so that hash is not a strong secret for the tunnel address. Your real public IP is not an input. The VPN server id is logged in the clear. That id names our server, not you.

The node then installs the peer with a public key, a preshared key, and the tunnel addresses that peer may use. It does not set your real address on the peer. After packets arrive, kernel WireGuard holds the current remote address so it can send packets back. The agent reads byte counters and the last handshake time from that state. It does not copy the remote address into those reports or into the database.

While the peer exists, a person with access to the server can look at live WireGuard status and see the current endpoint. That is the address of a connected peer at that moment. We do not write that status into the account database, and the cluster backup is built so it does not archive it. It is not a connection history we keep. The kernel also tracks active forwarded flows so routing works. This repository does not archive that table. An operator on the machine can inspect current flows. We do not keep a destination log.

The origin proxy also keeps rate-limit counters in memory, keyed by the same connecting address when Cloudflare sends it. Access logs are off, so those counters are not an access log on disk. They are gone when the proxy process restarts.

Logs and how long data is kept

The production log level is info. The peer-created log is described above. Some agent lines about an expired or stale peer include the internal peer id in the clear. They do not include the real public IP.

Origin nginx and the ingress controller have access logs turned off. We do not keep a separate access-log archive. Origin nginx sends its error log to /dev/null, so a failed request is not kept with the client IP. This nginx build cannot redact the client address inside an error line, and a pipe to a filter can refuse to start, so the log is discarded instead. The ingress controller's own error log is not turned off in this repository. A failed request there can still produce a line that includes the client IP. That line stays in the controller process log. This repository does not set how long the platform keeps it, and we do not copy it. Cloudflare may retain its own edge logs. We do not control that retention, and we do not keep a copy.

The Stealth listener is started at error log level, on the VPN node and in the cluster. A warning would record the stealth path. Error lines can still be written. This is not a browsing log.

Redis is started with snapshots and the append-only file turned off, with a memory cap that evicts keys under pressure. It is a cache.

  • Authentication rate-limit keys include the client IP. Some also include an email address or an Account ID. Sign-in counters expire after 1 minute. The longest of these windows is 1 hour (account creation, verification resend, and the password-reset hourly limit).
  • The website privacy checks (IP, DNS session, and breach) send the visitor IP to our API. That API stores a SHA-256 hash of the IP as a one-minute counter key, not the raw IP.
  • The phishing check keeps the visitor IP in process memory for a one-minute limit, and sends it to Cloudflare Turnstile with the challenge token. It does not write the IP or the checked URL to a log line.
  • When another security check is required, we send the client IP to Cloudflare Turnstile with the token. We do not write that IP down after the check.
  • Removed peers, including device metadata, keys, the tunnel IP, and the last handshake time, are deleted 30 days after removal.
  • Refresh-token hashes last 7 days, or until you sign out or delete the account. Verification and reset token hashes last 1 hour and 20 minutes. Unverified email accounts last 72 hours.

Events such as "peer created" and "account registered" are published on NATS. JetStream is enabled and can store data on disk, but this repository does not create a stream that captures those subjects. The account event carries the account type (email, anonymous, or device), not the email address and not an IP. The registration log stores a short hash of the account id, and for an email account a short hash of the email.

Backups

The cluster backup dumps the Veritas database and the BTCPay database, Kubernetes config and secrets, and the server WireGuard private key. It does not run a WireGuard status command into the archive. That status output would contain each peer's real public IP, which is why it is left out. Before the archive is encrypted, a check refuses to continue if the staging directory contains a peer endpoint. Local archives older than 14 days are deleted. Encrypted copies in Cloudflare R2 are deleted after 60 days by default.

The database includes the VPN server's own address. That is the address clients connect to. It is not your address. The peer table has no endpoint column and no client-IP column.

A separate postgres backup script, where it is used, keeps 7 daily, 4 weekly, and 3 monthly copies. Monthly copies are removed after about 93 days. It encrypts with GPG when a recipient is configured. Single-node recovery snapshots are removed after 35 days. Those scripts also strip peer endpoints from WireGuard text they copy.

No backup contains a real user IP. On October 24, 2026 an operator deleted every older backup that contained a WireGuard endpoint or a real user IP, both on the server and in off-site Cloudflare R2. Only a clean backup taken after that fix remained. The repository does not perform that deletion by itself. The operator did. New archives follow the retention windows above, and the current scripts still refuse to archive a peer endpoint.

A deleted account can remain inside a backup until that backup expires. We do not use backups to restore a deleted account into the live service except to recover from an incident.

Monitoring

Prometheus keeps 21 days of metrics, with a 10 GB cap. The VPN agent exports peer counts, aggregate bytes in and out, DNS request and block counts, blocklist size, and error counters. DNS block counters are labeled by category only. There is no per-user label, no query name, and no client IP. Database, Redis, node, and probe exporters report whether those systems are up. They are not a browsing log.

An uptime worker checks whether the website, the API, billing, the egress check, and the Stealth listener answer. It stores success and failure counters. It can send a Telegram message that names which check failed. That message does not include a visitor IP.

DNS and Veritas Shield

Shield is a DNS filter for WireGuard clients that use the in-tunnel resolver. Premium starts with malware, phishing, scam, cryptomining, and tracker names blocked. Ads and adult domains stay off until that Premium user turns them on. A block is an NXDOMAIN answer. It does not remove ads or trackers inside a page.

Allowed lookups are not stored. A block is not written to a log. When a name is blocked:

  • The gateway keeps that name in a deduplication map for up to 10 minutes, together with the tunnel IP and the category, so the same block is not announced again. The notice the app can show stays in gateway memory for up to 90 seconds.
  • A Redis key holds that notice for 2 minutes (120 seconds), keyed by the tunnel IP. Redis is not writing snapshots or an append-only file. The key is deleted when the peer is removed.
  • Session block totals, with no names, are keyed by the tunnel IP. They expire after 2 hours without a refresh, or when the peer is removed.
  • Account totals by category, with no names, are kept for 8 days and deleted when the account is deleted. Memory pressure can drop them sooner.
  • Prometheus keeps the aggregate counts, labeled by category and not by name, for 21 days.

Names that are not blocked are forwarded with DNS-over-HTTPS to cloudflare-dns.com and dns.google. Those providers see the hostnames. The list of names we refuse is downloaded and can be cached on disk. That file is the public filter list, not a record of your lookups.

Apps, checks, and diagnostics

The Android app does not request a location permission. The connection map draws a fixed point for the server in Paraguay. It does not read the device location. The Linux app map is the server location as well.

After the Android app connects, it asks api.ipify.org, ifconfig.me, and icanhazip.com for the public address seen through the VPN. Those requests are bound to the VPN network, including in Stealth mode. We do not store the address they return. The Linux app asks api.ipify.org for the same kind of egress check. It does not contact ifconfig.me or icanhazip.com. The Chrome extension is not yet available (coming soon). It can ask ipwho.is for an approximate location so its map can draw a pin, and it can contact api.ipify.org. The result stays in the extension. The extension does not log destination sites on our servers.

Diagnostics stay on the device unless you turn sharing on and send the report yourself, from your own email app. A report can include the app version, OS, device model, connection state, transport, handshake age, server address, and a sanitized last error. It does not include WireGuard keys or session tokens. We do not receive it unless you send that email.

The IP check on this website returns the request IP and coarse Cloudflare edge data for that page view, and your browser can load an OpenStreetMap map from it. We do not build a profile from it. The DNS leak test resolves short-lived names through edns.ip-api.com. We do not operate that DNS authority and we do not store those query names. The breach check sends the email you type to our edge function and then to XposedOrNot. We do not store that email. The browser check can open a WebRTC connection to a Google STUN server, and it can ask api64.ipify.org about IPv6. Those calls happen in your browser. We do not store the result.

Some download pages preconnect to fonts.gstatic.com. That request can send your IP address to Google. Those pages do not load a font stylesheet. The marketing homepage does not preconnect.

Third parties

We do not sell personal data. These parties appear in the service:

  • Cloudflare — website hosting, the tunnel in front of the origin, Turnstile, R2 backup storage, and DNS-over-HTTPS for names Shield forwards. Cloudflare sees client IPs for site and API traffic under Cloudflare's own policies.
  • Google — DNS-over-HTTPS for names Shield forwards, Google Play Billing, the font preconnect on some download pages, and the browser check's STUN server.
  • Resend — verification and password-reset email. The message includes the address it is sent to.
  • The mailbox for contact@veritasvpn.cloud — messages you send us, including the address you wrote from.
  • BTCPay — self-hosted by us, for Bitcoin invoices.
  • api.ipify.org, ifconfig.me, icanhazip.com, api64.ipify.org, ipwho.is, edns.ip-api.com, and XposedOrNot — the checks described above.
  • GitHub — only if you file a public issue.
  • Telegram — operational alerts to us. A new-account alert says the account type. A payment alert says the payment method, and whether it was a trial. Those messages do not include an email address, an Account ID, or an IP address. Uptime alerts name the failing check.
  • OpenStreetMap — map tiles loaded in your browser during the IP check. We do not receive a copy of that tile request beyond what Cloudflare already sees as ordinary site traffic.

If we are asked for data

We review requests. We require valid legal process under Paraguayan law, or another process we are legally required to honor. We narrow the request to what the order covers. We tell the user when the law allows it.

If compelled, the live systems could produce an email address when the account has one, a password hash, session-token hashes, device and tunnel metadata, the last handshake time, and payment records, including a Play purchase token or a provider transaction id stored on our side. BTCPay could produce invoices tagged with an account ID.

We cannot produce browsing history, a DNS query log, traffic contents, or your real connection IP from the account database, the connect log, or a backup. No backup contains a real user IP. On October 24, 2026 an operator deleted every older backup that contained a WireGuard endpoint or a real user IP, on the server and in off-site R2. A live look at WireGuard on the server can show the current endpoint of a peer that is connected at that moment. A blocked name can exist only for the short windows above. Redis rate-limit keys and a Turnstile check exist only for their windows. Cloudflare may have edge logs we do not hold. The warrant canary is the public statement about secret orders.

Limits, stated plainly

  • One operator runs the service. There is no second organization holding the keys.
  • No independent audit has been published.
  • We keep accounts, payments, peer metadata, operational logs, and aggregate metrics. This page does not say otherwise.
  • The database, Prometheus, the DNS filter-list cache, and backups are on disk. No backup contains a real user IP. Live kernel state on the VPN server still has the current endpoint of a connected peer.
  • Cloudflare and the upstream DNS providers see data that we do not store ourselves.
  • Paraguay is not the subject of a European Commission adequacy decision. We have not appointed an EU or UK representative. Using the VPN means account and tunnel metadata are processed in Paraguay, because that is where the service runs.
